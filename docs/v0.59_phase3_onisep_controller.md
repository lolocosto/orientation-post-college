# v0.59 — Phase 3 : Refactoring `onisep_extraction_controller.js`

## Principe directeur

C'est au **contrôleur** de créer et enrichir les établissements, pas au DatabaseService. Le nouveau flux inverse l'ordre : les établissements sont créés à partir des **relations** (qui portent UAI+nom), puis enrichis par les données du dataset **structures**.

Toutes les résolutions UAI → _id utilisent maintenant la **clé composite (UAI, nom)** au lieu de l'UAI seul, éliminant le bug racine identifié dans l'audit (F1 : deux structures partageant le même UAI comme Lycée VHB et Micro-lycée VHB).

---

## Nouveau flux `#processAndStoreAllData`

### Avant (v0.58)

```
Étape 1 : Stocker diplômes
Étape 2 : Stocker relations diplôme-étab (sans etabId)
Étape 3 : Construire étabs uniques par Map<UAI, etab> → stocker  ← 🔴 BUG : perd les doublons UAI
Étape 3bis : Autres diplômes niv 5+
Étape 3ter : Enrichir depuis actions (par UAI seul)
Étape 4-9 : Dispositifs, options, spécialités (résolution par UAI seul)
Étape finale : enrichirRelationsAvecEtabId (rattrapage par UAI seul)
```

### Après (v0.59)

```
Étape 1 : Stocker diplômes (inchangé)
Étape 2 : Construire relations diplôme-étab
         → CRÉER les établissements minimaux {_id, uai, nomOnisep, voies:['scolaire']}
           pour chaque couple unique (UAI, nom) trouvé dans les relations
         → Remplir etabId dans chaque relation
         → Stocker les relations
Étape 3 : ENRICHIR les étabs déjà en base depuis le dataset structures
           retrouvés par clé (UAI, nom), avec fallback UAI seul si 1 seul étab
Étape 3bis : Autres diplômes niv 5+ (inchangé, utilise uaiToIds)
Étape 3ter : Enrichir depuis actions par UAI+nom via #resolveEtabId
Étape 4-9 : Dispositifs, options, spécialités — résolution par UAI+nom via #resolveEtabId
(plus d'étape finale de rattrapage — les etabId sont résolus dans chaque étape)
```

## Méthodes créées

### `#creerEtablissementsMinimaux(diplomesParEtablissementMap)` → Map<UAI, [_id]>

Parcourt les relations diplôme-établissement. Pour chaque couple unique (UAI, nom) :
1. Insère un établissement minimal `{uai, nomOnisep, voies: ['scolaire']}` via `insertEtablissement()`
2. Remplit `relation.etabId` avec l'_id obtenu
3. Construit la map `uaiToIds` (UAI → [_id]) pour les étapes suivantes

Le **nom** de l'établissement vient du champ `etabNom` ajouté dans le parser (phase 2), avec fallback sur l'UAI si absent.

### `#enrichirEtablissementsDepuisStructures(rawData, uaiToIds)` → number

Enrichit les établissements minimaux avec les données complètes du dataset structures :
1. Pour chaque structure avec un UAI ayant des relations → cherche par `getEtabIdByUaiNom(uai, nom)`
2. Si trouvé → `updateEtablissement(etabId, updates)` (enrichissement non-destructif)
3. Si pas trouvé mais un seul étab pour cet UAI → fallback sur celui-là
4. Si pas trouvé et plusieurs étabs → warning (différence de nom entre datasets)

### `#resolveEtabId(uai, etabNom, uaiToIds)` → string|null

Utilitaire de résolution UAI+nom → _id, utilisé partout :
1. Si `etabNom` disponible → recherche précise via `getEtabIdByUaiNom()`
2. Sinon fallback UAI seul via `uaiToIds` (prend le premier, warning si ambiguïté)

## Résolution du bug racine (F1 de l'audit)

**Avant** : `etablissementsMap.set(etab.uai, etab)` → Map<UAI, etab> → le Micro-lycée VHB (même UAI 0352009U) n'est jamais inséré.

**Après** : chaque relation porte `(uai, etabNom)` → `insertEtablissement()` crée un enregistrement par couple unique (UAI, nom). Deux structures avec le même UAI mais des noms différents → deux établissements distincts en base.

## Compatibilité

- Ce fichier **dépend** des phases 1 et 2 (nouvelles méthodes `getEtabIdByUaiNom()`, `updateEtablissement()` non-destructif, et `etabNom` dans les relations du parser).
- Il utilise encore le **wrapper deprecated** `getOrCreateEtablissementId` nulle part (référence supprimée).
- Les wrappers deprecated de la phase 1 restent disponibles pour les **autres contrôleurs** non encore migrés (CARIF, data.education).
